# Known limits

This is a functional foundation. It does not yet meet the full system definition in the two root build prompts.

- The provided workspace has no `.git` directory, so the prompt's per-phase commit requirement cannot be satisfied in this checkout as-is. No repository history was initialized or fabricated.
- SQLite migration version 2 creates runtime checkpoint storage and the connector, grant, library, history, item metrics, LLM call, update, settings history, and expanded proposal data structures. Approval continuation state is now encrypted in the checkpoint table and recovered after restart; most of the new Phase 16 tables still lack their API workflows.

- Mock, OpenAI-compatible, and Anthropic provider adapters and a bounded non-streaming tool-call loop exist. Only the mock provider and scripted tool loop have been exercised here; real provider connectivity requires environment configuration and credentials. Streaming model deltas, cancellation propagation into outbound HTTP, agent-initiated delegation, fine-tuned routing, embeddings, and training are not implemented.
- The tool loop exposes workspace read/list/search/write/edit, shell execution, task creation, memory, Git inspection, and run-scoped worker communication. Risky tools pass policy and approval checks. Checkpoints survive daemon restart and resume the exact provider transcript. Browser, desktop, network fetch, and connector tools remain catalog-only.
- Agent profiles now store and load a system prompt, responsibilities, tool/skill allowlists, permission tier, step/token limits, and schema/example/dependency fields, but only five distinct profiles are seeded and there is no profile editor/version history. The skill library remains five starter entries. The requested 100+ agents / 200+ skills and 20,000-run dashboard scale test are not present.
- MCP currently supports explicitly trusted stdio servers with namespaced tools, workspace-jail for the working directory, per-agent grants, timeouts, status, and a local fixture. Streamable HTTP transport/authentication, exponential reconnect/backoff, comprehensive collision/recovery testing, and service connectors (Gmail, Calendar, Drive, GitHub, Slack) remain unimplemented. No external user data is connected.
- No remote team hub, VS Code extension, desktop accessibility integration, browser automation, shell sandbox, updater, signed update manifest, or lifecycle forge/janitor is implemented.
- The static dashboard has no automated browser accessibility, responsiveness, or large-catalog performance suite yet. Approval and proposal review endpoints work; approving a proposal only changes its status and does not mutate library contents.
- The landing dashboard now has a local orchestration canvas with parent/worker activity, SVG dependency edges, hover-based message/tool/provider and workspace-file artifact inspection, direct agent/provider run overrides, and automatic provider selection by agent specialty. Run-level provider override applies to planner and workers. Workflow definitions persist through API create/read/update/delete/run; the dashboard supports multi-step create/edit/run. Active runs subscribe to persisted SSE events with polling fallback; browser-level stream rendering has not yet been verified. Integration covers workflow persistence/run, actual selected provider/model, and an approved file artifact in canvas data. Plugin/connector attribution and repeatable browser verification of graph/artifact/live behavior remain outstanding; see `IMPLEMENTATION_TODO.md`.
- The task board can create and move tasks. The memory explorer can save and search currently loaded records in the browser, but server-side full-text search, per-user ACLs, edit/delete/pin, and retention cleanup are not implemented.
- The HTTP service is single-user and local-only. It does not implement a remote API, WebSocket event stream, reverse-proxy support, or production session rotation/revocation.
- Provider profiles support create/edit/enable/default/test/delete, endpoint validation, timeouts, model limits, masked keys, and runtime token accounting. Fake-server integration proves a selected profile drives a complete run. Secrets use native OS vault adapters and stay off command arguments; macOS Keychain is smoke-tested, while Linux/Windows vaults and VS Code extension-host wiring remain unverified. DNS validation is not pinned to the actual connection, and external provider connectivity has not been tested.
- Per-agent and per-task provider routing are exercised end to end with fake providers; a research agent auto-routes to a DeepSeek-named profile. Disabling or deleting a profile clears agent assignments so the runtime falls back to automatic routing instead of retaining a broken reference. Browser tests for provider profile form round-trips and live model display remain outstanding.
- Runs can be queued asynchronously and stream persisted run events over SSE. The planner asks the selected provider for a bounded JSON plan, validates it against active agent IDs and dependency rules, and falls back to the local heuristic plan when needed. The scheduler runs ready workers in batches of at most three, blocks dependent stages, and enforces a shared 30,000-token run budget. Child runs/subtasks, worker results, messages, blackboard entries, and child lifecycle events persist on the parent timeline. Workers can send run-scoped messages, read their inbox, and publish/read shared blackboard values. The dashboard shows plan stages, shared blackboard, live worker events, and final supervisor summary. Agent-initiated delegation, cost budgets, worker retries, SSE cursor replay, and cross-run scheduling remain outstanding.
- Shell execution uses a no-network OS sandbox on macOS and Linux, but automated tests currently cover macOS only; see the shell execution section below. A complete typed tool registry, resource quotas, and destructive-command/escape tests are still missing.

These omissions are explicit. No integration is represented as connected or verified when it is not.
# Shell execution

`shell.exec` now runs through an OS sandbox on macOS and Linux, but current automated coverage is macOS-only. Linux bubblewrap availability is not bundled or verified. The runner denies network and restricts filesystem writes to the selected workspace, limits each invocation to 10 seconds and 256 KB of captured output, and propagates cancellation. CPU and memory quotas are not yet enforced; the shell acceptance suite remains open in `IMPLEMENTATION_TODO.md`.
