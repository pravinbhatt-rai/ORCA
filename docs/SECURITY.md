# Security boundaries

- Bind dashboard service to loopback only. Host header allow-list rejects unknown names.
- The local dashboard has no bootstrap/login token; access is limited to the loopback bind and host allow-list. Mutating requests still reject cross-origin origins.
- CSP blocks remote scripts, styles, frames, objects, and base URL changes. Dashboard assets are local and no remote assets are loaded.
- API records and audit details pass through redaction. Sensitive field names are replaced, common API-token patterns are masked, and email addresses are masked.
- Provider secrets are stored through native OS vault adapters: macOS Security.framework, Linux Secret Service, or Windows Credential Manager. Values travel to helper processes through stdin rather than argv; references only are kept in SQLite. A VS Code `SecretStorage` adapter is available, but extension-host wiring and Linux/Windows native vault runs remain unverified. The current macOS Keychain implementation has a real round-trip verification.
- OpenAI-compatible profile endpoints must use HTTPS remotely or HTTP on loopback; private/local IP literals, private DNS answers, URL credentials, queries, and fragments are rejected. Provider calls have per-profile bounded timeouts. DNS results are checked before `fetch` but are not pinned to the connection, so DNS rebinding protection remains incomplete.
- HTTP errors use structured envelopes with stable codes, request IDs, safe messages and remediation suggestions. Invalid JSON and oversized bodies have distinct codes; provider test failures and server logs avoid raw transport/provider messages and stack traces. The complete typed error matrix and SSE/runtime error envelopes remain open work.
- Approval arguments are stored redacted and bound to a SHA-256 hash. Decision requests must echo the same hash; changing reviewed args invalidates the approval. `send` tier always asks.
- Pending tool calls, the model transcript, and the shared worker budget are serialized as AES-256-GCM authenticated ciphertext in `runtime_checkpoints`. The 32-byte checkpoint key is generated under the private data directory with mode `0600`; the directory is restricted to `0700`. Startup recovery rechecks the approval status and argument hash, then re-evaluates policy before executing. File writes and edits compare captured pre/post images to avoid applying the same change twice; task and memory creation use deterministic run/tool-call IDs.
- The checkpoint key is stored beside the database. This protects database-only copies and exports from exposing suspended prompts/arguments, but does not protect against an attacker who can read the full data directory or run as the same OS account. The key is not a replacement for the cross-platform OS keychain work.
- Policy configuration supports validated allow/ask/deny modes by risk tier, tool, workspace, and session. Policy decisions are checked in the runtime before the tool implementation and can deny or request approval; persisted workspace decisions are available in the policy API. Session decisions are process-local. Untrusted inputs can be marked with `wrapUntrusted`; tainted context forces approval for risky follow-up actions, even when a session or workspace grant would otherwise allow them.
- Workspace reads/search, filesystem writes/edits, task and memory actions, git inspection, and shell execution have runtime implementations. Shell uses a no-network OS sandbox on macOS and Linux; CPU/memory quotas and Linux test coverage remain open. Browser, desktop, and connector tools remain catalog-only.
- The app is single-user and loopback-local; do not expose the port outside the allow-listed loopback hosts.

See `KNOWN_LIMITS.md` for unimplemented hardening, ACL, and sandbox work.
